# Каркас документа «Архитектура решения человеческим языком»

Полный аннотированный шаблон для `plans/architecture/YYYY-MM-DD-<имя>.md`. Это второй слой скилла `solution-blueprint` — читай, когда уже пишешь документ.

Калибруй объём: правка на один экран — короткий документ (что есть → что делаем → один макет было→стало → одна развилка). Новая фича на несколько экранов — полный каркас. Документ для **человека** — лучше короче и яснее, чем полно и нечитаемо.

---

## Frontmatter (целевой)

```yaml
---
type: architecture
status: draft            # draft → approved ТОЛЬКО после явного «да» владельца
feature: <kebab-имя>     # совпадает с feature анализа и будущего ТЗ — по нему tz-author найдёт файл
date: YYYY-MM-DD
owner: <кто одобряет — владелец>
relates_to:
  - plans/analysis/YYYY-MM-DD-<имя>.md   # вход-анализ, если был
  - plans/tz/YYYY-MM-DD-<имя>.md          # путь будущего ТЗ (резервируем имя)
  - second-brain/<профильная заметка по фиче>.md # профильная заметка
  - plans/analysis/<имя>-prototype/index.html # прототип-эталон, если есть
approved_at:             # YYYY-MM-DD при approved; пусто пока draft
---
> Что это: <одно предложение, что строим>. Для кого: <роль человеческими словами>.
> Цепочка: анализ `plans/analysis/...` → **эта архитектура** → ТЗ `plans/tz/...`
> Статус согласования: <дата, когда владелец одобрил, или «ожидает одобрения»>
```

`feature` — критичен: `tz-author` ищет архитектуру по совпадению этого slug. Держи единым через анализ → архитектуру → ТЗ.

## Разделы документа (по порядку)

### 1. Что это и зачем
Одно-два предложения сути + кто страдает сегодня и как. Роли — человеческими словами ({{PERSONAS}}), не техническими идентификаторами вроде «host/admin/tenant». Боль конкретная.

- ✅ «Пользователь при входе видит сетку из ~10 виджетов-цифр — числа без истории. Не понимает, как идут дела, пока не полистает и не посчитает в уме.»
- ❌ «Дашборд имеет низкую usability и требует cognitive load для интерпретации метрик.»

Метафора, выравнивающая образ, тут уместна: «разворачиваем экран на 180° — сверху рассказ, цифры вниз».

### 2. Как сегодня (от чего отталкиваемся)
Текущее поведение/функционал простым языком — это «какой был функционал» из запроса владельца. Из baseline (RepoBrain), но **без имён сервисов/таблиц/эндпоинтов**. Цель — владелец понимает стартовую точку и масштаб изменения.

- Если что-то уже частично работает, но спрятано/сломано — скажи прямо («таблица уже есть, но недостижима с главного экрана»). Это бережёт от «переписать то, что есть».

### 3. Что делаем (решение простыми словами)
Суть решения. Что меняется для пользователя. Расширяем существующее или делаем новое — назови честно (это масштаб для владельца). Без «как» на уровне кода.

### 4. Как это будет выглядеть (ядро — три приёма)

#### 4а. Сценарии «было → стало»
Для каждого ключевого пути. Шаблон:

```
**Сценарий: <название пути, человеческими словами>**
- Было: <что пользователь делает сейчас> → <что видит> → <чем недоволен>.
- Стало: <что делает> → <что видит> → <какой исход/польза>.
```

Один сценарий = один пользовательский путь. Не «функция X» — а «пользователь хочет Y».

#### 4б. Макеты экранов — по умолчанию кликабельный HTML

Всё, что имеет UI, показывай страницей, которую владелец откроет и потыкает: инструмент `Artifact` публикует её ссылкой, страница читается с телефона; правила оформления — скилл `artifact-design`. Ссылка на макет кладётся в этот же раздел документа. Состав и расположение, не цвета/шрифты; состояния (пустое/ошибка/загрузка) показывай, если меняют смысл.

Требования к макету:
- одна страница — один пользовательский путь из «было → стало»;
- переходы между состояниями работают кликом (владелец должен ткнуть, а не поверить на слово);
- никакой боевой логики и настоящих данных — только вид и порядок экранов.

**ASCII-рамка — запасной вариант:** фича без интерфейса (фоновая обработка, формат данных, правило) или публикация недоступна. Пользуешься запасным вариантом — скажи об этом строкой в документе. Пример рамки (нейтральная иллюстрация приёма, не из конкретного продукта):

```
┌──────────────────────────────────────────────┐
│  ⚠️ Статус: требует внимания        Неделя 27  │   ← обложка-вердикт
│  ┌─Ось A──┐ ┌─Ось B──┐ ┌─Ось C──┐ ┌─Итог──┐   │
│  │ 🟢 Ок  │ │ 🔴 Риск│ │ 🟡Букс.│ │🟡 ...│    │   ← оси-светофоры, каждая «почему» одной строкой
│  └────────┘ └────────┘ └────────┘ └──────┘    │
├──────────────────────────────────────────────┤
│  [ Читать полную сводку ▾ ]                    │   ← одна кнопка, разворачивает текст
├──────────────────────────────────────────────┤
│  Блок 1        ▸ короткий вывод одной строкой  │
│  Блок 2   ↔ деталь / кто отвечает (клик→фильтр)│
│  [Показать цифры ▾]   ← прежние виджеты уехали  │
└──────────────────────────────────────────────┘
```

Подпиши стрелками `←` что есть что и что меняется при действии. Цель — владелец ткнёт «вот этого тут быть не должно» / «а где X».

#### 4в. Живой образец (золотой пример)
Где применимо (отчёт, письмо, чат-ответ, экран с контентом) — **конкретный заполненный пример реальными словами**, не «тут будет текст отчёта». Нейтральный образец приёма:

```
**⚠️ Требует внимания** · Неделя 27

_Двумя словами: в целом стабильно, но неделю держат две вещи —
<ключевой риск 1 своими словами> и <ключевой риск 2 своими словами>._

- Ось A — Ок · <короткая причина одной строкой>
- Ось B — Риск · <конкретный факт, а не «плохо»>
...
```

Живой образец ловит несоответствие тона/состава мгновенно — это сильнейший антидот к «не то имел в виду». Тон бери из раздела о позиционировании/тоне в `second-brain/` (как мы говорим о продукте).

### 5. Делаем поверх существующего (масштаб своими словами)
Главный вопрос владельца — «это большая стройка или небольшое расширение?». Ответь человеческим языком: «это расширение того, что уже работает — новых умных частей не плодим» ИЛИ «новый раздел с нуля». Можно перечислить, что переиспользуем — но **названиями-функциями для человека** («существующий ночной сбор отчёта», «готовые сводки»), без листинга полей/таблиц. Глубокий reuse-маппинг (`path:line`, имена сервисов) — добирает `tz-author` сам через RepoBrain; здесь — только масштаб и принцип «не плодим лишнего».

### 6. Границы — что НЕ делаем
Простыми словами, что осознанно за рамками — чтобы владелец не ждал лишнего. Каждый отложенный кусок — с короткой причиной и (если знаешь) «на потом». Это вход в `Scope: не входит` ТЗ.

- «Раздел X в отчёт пока не берём — нет источника данных. Отдельной задачей позже.»

### 7. Дорешал сам
Заголовок раздела — **дословно «Дорешал сам»**: по нему проверяется контракт выхода звена. Продуктовые развилки, закрытые тобой (на основе анализа/кода/рекомендации). Таблица:

| # | Решил | На чём стою |
|---|---|---|
| Р1 | Недельную сводку собираем из 5 дневных, а не пересчитываем неделю заново | Дёшево; то, что ты уже читал по дням, не разойдётся с недельным итогом |

Владелец читает и может возразить — это дешевле, чем поймать на коде. Развилку, которую закрыл анализ рекомендацией, перенеси сюда простыми словами.

Раздел обязателен **всегда**, даже когда вопросов владельцу не было: тогда в нём стоит явная строка «владельцу вопросов не задавал, потому что …». Пустой раздел и отсутствующий раздел читаются одинаково — как «звено не отчиталось».

### 8. Что реши ты (открытые развилки)
Только **реальные продуктовые** развилки (меняют что видит/делает пользователь И не решаемы за владельца обоснованно). Каждая — с рекомендацией:

> **Тон текста: сухо-деловой или «личный ассистент»?**
> Рекомендую «личный ассистент» (как в образце выше) — он держит внимание и отражает позиционирование, а не «отчёт-выгрузка». Не так — поправь.

Технические развилки («расширять сервис или новый», «sync vs очередь») сюда НЕ выноси — это `tz-author`.

### 9. Как поймём, что получилось (глазами пользователя)
Критерий «сделано» так, как его проверит человек, не машина:
- «Пользователь за 30 секунд после входа понимает, как идут дела, не листая виджеты.»
- «Гость заходит по ссылке без регистрации и сразу видит результат.»

Это вход в acceptance ТЗ — `tz-author` переведёт в машинные предикаты (что грепать, какие тесты). Здесь — человеческий исход.

### 10. Связи
Ссылки: вход-анализ, путь будущего ТЗ, прототип-эталон, профильная заметка в `second-brain/`. Одной строкой «дальше → ТЗ `plans/tz/...`».

## Протокол точки одобрения (draft → approved)

1. Документ дописан, `status: draft`.
2. В чат — **короткое резюме** (3–6 строк), не пересказ файла: что строим · как выглядит одной фразой · главные решения за владельца · что осталось решить ему. Ссылка на файл за деталями.
3. Явный вопрос: «Это то, что ты имел в виду? Одобряем или правим?» + открытые развилки Шага 8 батчем (с рекомендациями), через `AskUserQuestion` или текстом.
4. Реакция владельца:
   - **«да / одобряю»** → `status: approved` + `approved_at: <дата>`; назови путь ТЗ; скажи, что `tz-author` теперь возьмёт архитектуру.
   - **правки/возражения** → внеси в документ, покажи снова, остаёшься в `draft`.
5. **Никогда не ставь `approved` сам.** Это «решение владельца» (необратимо влияет на продукт). Автономия — про реализацию, не про продуктовое одобрение замысла.

## Человеческий язык vs жаргон (грепни перед показом)

| ❌ Жаргон (провал звена) | ✅ Человеческий язык |
|---|---|
| «Добавляем эндпоинт `GET /...` с валидируемой схемой» | «Главный экран начнёт показывать готовую сводку за период» |
| «Расширяем сущность данных тремя полями» | «К сводке добавляем вердикт, текст и цель» |
| «Синтез через map-reduce, один проход модели, сохраняем снапшот» | «Система сжимает каждый источник отдельно, потом собирает связный рассказ и запоминает его» |
| «Виджет осиротел: зарегистрирован в пресетах, но привязан к режиму X» | «Таблица уже построена, но до неё нельзя добраться с главного экрана» |

Допустимое исключение — раздел 5 «делаем поверх существующего», где краткое упоминание «что переиспользуем» функциональными именами помогает владельцу понять масштаб. Везде ещё — перевод обязателен.

## Антипаттерны каркаса
- **Документ-отчёт вместо документа-решения** — пересказал анализ, но не показал «как будет выглядеть». Владельцу нужно увидеть результат, а не прочитать исследование заново.
- **Пропущенный живой образец** там, где есть контент (отчёт/письмо/экран) — абстрактное описание не ловит рассинхрон тона.
- **Технические развилки, вынесенные владельцу** — он не должен решать «sync или очередь».
- **approved без явного «да»** — ломает весь смысл звена.
- **Дубль анализа** — копипаст разборов вместо ссылки и выводов.
