# Доказательство выбора и состязательная перепроверка

Метод: всё исследовать → найти лучшее → **доказать** → **перепроверить независимо**. Представляй варианты, доказывай выбор.

## Gap-таблица «конкурент × наш проект» (обязательная)
| Возможность | Лучший конкурент (как именно) | Что у нас сейчас (code-baseline) | Дельта / что строить |
|---|---|---|---|
| … | … | … | table-stakes (догнать) / обгон |
Прямой главный вход для tz-author: видно, где догоняем рынок, а где закрываем недо-обслуженный исход (ценнее).

## Feature-матрица vs JTBD-матрица
- **Feature-матрица** — по table-stakes, статусы **полностью / частично / нет** (НЕ бинарно да/нет).
- **JTBD-матрица** — строки = шаги работы пользователя проекта, ячейки = насколько полно/с каким трением конкурент закрывает шаг. Вскрывает gap'ы уровня исхода, а не фичи. Прямой вход в раздел ценности ТЗ.

## Матрица вариантов
2–3 кандидата (один вариант = замаскированное решение). `Критерий | A | B | C` + **источник каждой оценки**. 4–7 критериев = ограничения проекта (`{{PROJECT_CONSTRAINTS}}`), напр.: границы MVP · архитектурные инварианты · единый стек · ключевой продуктовый дифференциатор · разнесение прод-нод · multi-tenancy · стоимость внешних вызовов.
Критерий «лучше» = пригодность под ограничения проекта, **НЕ популярность технологии у конкурента** (анти-карго-культ). Оценивай чужое решение по тому, КАК оно используется под наш сценарий (масштаб/техдолг/опер-нагрузка).

## ADR-каркас (Architecture Decision Record)
```
Контекст (ограничения проекта) → Альтернативы (2-3, каждая в steelman-форме) →
Trade-offs (по критериям) → Рекомендация → Последствия (что принимаем/теряем)
```
Каждое решение нумеруй, колонка «Почему» + ссылка на правило/память. Ни одной открытой развилки без рекомендации.

## Assumption-mapping
| Допущение | Ось (desirability/viability/feasibility) | Критичность | Уверенность | Как проверить |
|---|---|---|---|---|
feasibility завязывай на ограничения проекта (`{{PROJECT_CONSTRAINTS}}`, `{{DOMAIN_HIGH_IMPACT}}`) — архитектурные границы, очереди/воркеры, multi-tenancy, маршрутизацию внешних вызовов. Вывод на непроверенном критичном допущении = гипотеза, не факт → в «Ограничения».

## Состязательный второй проход (ядро «перепроверить»)

**Запускается по триггеру:** развилка с двумя и более сильными вариантами · необратимое решение · затронуты деньги, доступ, данные. Ни один не сработал — второй проход не нужен, в анализе стоит честная строка «red-team не запускался, развилки не было». Steelman отвергнутых альтернатив (п.1) делается всегда — он стоит абзац.

1. **Steelman** каждой отвергнутой альтернативы — сильнейшая честная версия, не соломенное чучело.
2. **Red-team суб-агент** с задачей **опровергнуть** рекомендацию: контр-источники, контрпримеры.
3. **Независимый retrieval** — red-team стартует с ДРУГИХ запросов (не та же выдача), по возможности под другим углом. Иначе это self-consistency-иллюзия, не проверка.
4. **Стоп-условие:** один полный red-team-проход без новых опровергающих фактов → вывод выжил. Нашёл опровержение → переписать вывод, повтор. Макс. 2 раунда; не сошлось → вынести как HIGH-развилку владельцу.
5. Для каждой рекомендации явно: **на чём она ломается** (граничное условие).

## Защита от ловушек
- **Self-preference:** не засчитывай свой первый проход как «уже доказано».
- **Эхо-камера:** общая стартовая выдача у агентов = не независимость.
- **Volume ≠ validation:** много перепечаток одного релиза ≠ триангуляция.
- **Карго-культ:** «у всех так» ≠ «лучше для нашего проекта».
- **Деприоритизированная тема:** аспект, который владелец отложил, — нейтральный факт в матрице, НЕ вывод-блокер; и не тащи в анализ то, что владелец ещё не поднял.

## Evidence hierarchy (по убыванию веса)
первоисточник/код/релиз-ноут > независимый замер/доклад > отзывы (порог) > вторичная аналитика > вендор-маркетинг > соцсети/слухи.
