# Каркас аналитического документа

Для лёгкого разбора (чисто внутренняя фича, 1–2 источника) бери сокращённо: рамка проблемы → gap-таблица → матрица вариантов → рекомендация → источники. Для полноценного исследования — полная структура ниже, в подпапке.

## Целевой frontmatter
```yaml
---
type: analysis
status: research-complete   # draft пока идёт сбор; per-source = research-input
feature: <kebab-имя>
date: YYYY-MM-DD
snapshot_date: YYYY-MM-DD     # дата снятия данных
owner: <кто принимает продуктовые решения>
related: [plans/tz/...md, second-brain/01_projects/<feature>.md]
---
> Цель разбора: <одно предложение>. Snapshot: YYYY-MM-DD.
> Следующий шаг → архитектура (solution-blueprint): plans/architecture/YYYY-MM-DD-<имя>.md
```

## Подпапка для большого исследования
```
plans/analysis/YYYY-MM-DD-<имя>/
  00-index.md            (опц.) карта файлов + статус прогона
  _raw-query-*.md        (опц.) сырые выдачи суб-агентов как сырьё
  01-<сегмент>.md        per-source, status: research-input  (1 файл = 1 суб-агент)
  02-<сегмент>.md        ...
  99-synthesis.md        status: research-complete  ← это берёт tz-author
```
Маленькому разбору хватает одного файла без `99-synthesis`. `tz-author` берёт в работу только `status: research-complete`.

## Обязательные секции синтеза (99-synthesis)
1. **Рамка проблемы** — 1–2 конкурирующие формулировки, кто страдает (роли проекта), метрика «решено». Iceberg: симптом vs корень.
2. **Дерево вопросов (MECE)** — этапы потока фичи; это будущий каркас фаз ТЗ.
3. **Ландшафт аналогов** — по всем целевым рынкам (зарубеж/глобальный | локальный, если он есть), сгруппированы по силе пересечения (прямой / косвенный / процесс-без-продукта).
4. **Teardown'ы** ключевых игроков — по карточке (ниже), оба разреза.
5. **Gap-таблица «конкурент × наш проект»** — `Возможность | Лучший конкурент (как) | Что у нас сейчас (baseline) | Дельта/что строить`.
6. **Матрица вариантов** — 2–3 кандидата × 4–7 критериев (ограничения проекта `{{PROJECT_CONSTRAINTS}}`), источник каждой оценки; + JTBD-разрез.
7. **Рекомендация (ADR)** — контекст → альтернативы (steelman) → trade-offs → выбор + последствия.
8. **Открытые вопросы к владельцу** — каждый с рекомендацией + почему.
9. **Допущения и риски** — desirability/viability/feasibility × критичность × уверенность.
10. **Ограничения и непроверенное** — все `[unverified]`, устаревшее, bias-риск.
11. **Источники** — URL + дата + тип + тег `verified/claimed/inferred`.

## Шаблон карточки аналога (два разреза)
```markdown
### <Игрок> — <прямой|косвенный|процесс-без-продукта>
**Функционально (простым языком):** что это, для кого, как работает по шагам job-а пользователя.
Ролевая аналогия: «как <секретарь/архивариус>». Чем ценно.
> Гипотеза «почему так сделали»: <стратегия/приоритет, который это отражает>.

**Технически:** стек/архитектура/либы/лимиты [тег: verified|claimed|inferred + URL+дата].
Маппинг на наш стек: <как легло бы на {{PROJECT_STACK}}>. Чужой продакшен-код на другом языке → «портировать в стек проекта».

**Сильное / слабое (из отзывов):** <повторяющиеся жалобы → можем закрыть у себя?>
```

## Эталонный мини-образец 99-synthesis (скелет)
```markdown
# Анализ: экспорт данных пользователя (self-service выгрузка)
## Рамка проблемы
Формулировка A: «пользователь ждёт выгрузку через поддержку 2 дня» | B: «нет self-service экспорта → нагрузка на саппорт».
Страдает конечный пользователь + саппорт; метрика «решено» — 0 тикетов на выгрузку в 90% случаев.
## Дерево вопросов (MECE)
запрос экспорта → сбор данных → упаковка/формат → доставка (ссылка/почта) → срок жизни файла. [ветви → фазы ТЗ]
## Ландшафт
Зарубеж/глобальный: Конкурент-A, Конкурент-B, Конкурент-C. Локальный (если есть рынок): Конкурент-D. [карточки ниже]
## Gap «конкурент × наш проект»
| Self-service экспорт | Конкурент-A: async + ссылка на почту | У нас: только ручная выгрузка через саппорт | строить async-воркер |
## Матрица вариантов
| Критерий (источник) | A: синхронный inline-экспорт | B: фоновый воркер + ссылка |
| Стоимость/нагрузка ($/операция) | … | … |
## Рекомендация (ADR): B — фоновый воркер. Почему: большие выгрузки не держат HTTP-запрос/не роняют процесс. Последствия: …
## Открытые вопросы: 1) … (рекомендую X, потому что Y)
## Ограничения: бенчмарк скорости упаковки Конкурент-A — [claimed], независимого замера нет [unverified].
## Источники: …
```

## Good / bad признаки
- OK Сегментация по типам конкурентов; подпапка per-source (1 файл = 1 суб-агент) с единой `snapshot_date`.
- OK Технический разрез с явным маппингом на стек проекта; найденный чужой продакшен-код на другом языке помечен «портировать».
- OK Функциональный разрез простым человеческим языком (владелец читает без стек-жаргона).
- BAD Дрейф цифр между связанными доками («80k» vs «100k+») — лечится единой `snapshot_date` + trace-to-original.
