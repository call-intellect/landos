# Проверка глазами пользователя (B5 / финал контура A)

Код, который «должен работать», и код, который работает, — разные вещи. Ты — глаза
владельца: открываешь его продукт как чужой человек и проходишь сценарии руками.
Никакой вердикт «готово» в проекте не выдаётся без твоего прохода.

## Инструмент

Browser-MCP (Playwright): `browser_navigate` / `browser_snapshot` / `browser_click` /
`browser_type` / скриншоты / консоль. Если MCP не поднят — подними по конфигу кита;
проверка «по коду, без браузера» запрещена.

Приёмы (донор — официальный webapp-testing):
- **Сначала разведка, потом действие:** сними snapshot/скриншот, пойми что на экране,
  потом кликай. Не жми вслепую по селекторам из кода.
- **Жизненный цикл сервера — отдельно от проверки:** подними dev-сервер (`{{DEV_CMD}}`)
  фоновым процессом, дождись готовности, проверяй; по завершении погаси. Не смешивай
  логи сервера с результатами прохода.
- **Не таскай мегабайты HTML в контекст:** точечные snapshot'ы и скриншоты, а не дампы
  страниц.

## Порядок

### 1. Собери сценарии
Источники, по приоритету: сценарии из ТЗ (plans/tz/) → сквозной сценарий из
product-brief → «было→стало» из architecture-блюпринта. Каждый сценарий = путь
пользователя: вход → действия → ожидаемый результат.

### 2. Пройди каждый сценарий
- Открой приложение (реальный URL: локальный dev или задеплоенный).
- Пройди шаги кликами/вводом, как человек. На каждом ключевом шаге — скриншот.
- Сверь экраны с ASCII-макетами/описаниями из блюпринта: то ли вообще построено?
- Читай консоль браузера: JS-ошибки и упавшие запросы — дефекты, даже если «выглядит нормально».
- Обязательные негативные проверки: пустая форма → есть ли внятная ошибка; повторное
  нажатие кнопки отправки; обновление страницы посреди сценария.

### 3. Вердикт
```
СЦЕНАРИЙ: <название>            ПРОШЁЛ / УПАЛ
Шаги: ... (где упал — скриншот)
Консоль: чисто / <ошибки>
Соответствие блюпринту: да / расхождение: <что>
```
- Все сценарии прошли → вердикт «работает», скриншоты — владельцу (он видит СВОЙ продукт).
- Что-то упало → НЕ чинить самому наспех: дефект с шагами воспроизведения →
  исправление обычным порядком; два неудачных фикса → `debug-recovery`.

### 4. Фиксация
Результат прохода — в приёмку фазы (tz-orchestrator) или в отчёт контура A.
Повторяющиеся сценарии → предложи закрепить как e2e-тест (стек-пак playwright-qa).

## Анти-паттерны
- ❌ «Тесты зелёные, значит работает» — тесты не видят сломанную вёрстку, мёртвую кнопку, CORS.
- ❌ Проверка только happy-path — новичок-пользователь жмёт не туда в первую минуту.
- ❌ Чинить найденное «по-быстрому» внутри проверки — смешиваются роли; дефект → отдельным порядком.
- ❌ Вердикт без скриншотов — владелец должен видеть, а не верить на слово.
