# Визуальная приёмка {{PROJECT_NAME}} (playwright-qa)

Скилл даёт два готовых доступа к тестовой среде, чтобы не вводить креды каждый раз:

| # | Доступ | Инструмент | Что делает |
|---|--------|-----------|------------|
| 1 | **UI приложения** | Playwright (MCP `browser_*`) | вход тестовым аккаунтом, клики, приёмка глазами, скриншоты |
| 2 | **Данные / «база»** | `<DIAG_CMD>` | read-only разбор данных сущности (цепочка обработки → состояние → логи) |

> ⚠️ Тестируешь на живой среде (`<APP_URL>` — прод или стенд). Действуй только под тестовым аккаунтом и не трогай данные чужих владельцев/тенантов. Любые **деструктивные** действия (удаление сущностей, смена чужих настроек, массовые операции) — только с явным «да» владельца в этой сессии.

## Где креды (читать в начале, НЕ переспрашивать)

Файл: `<CREDS_FILE>` — gitignored, читается Read-ом.

```json
{ "url": "<APP_URL>", "email": "...", "password": "...", "landingPath": "/" }
```

Правила:
- Прочитай файл Read-ом **один раз** в начале сессии тестирования.
- Пароль **никогда не печатай в чат** и не вставляй в коммиты/скриншоты. В Playwright подавай его прямо в `browser_type` (в UI-поле он маскируется).
- Файла нет / поля пустые → скажи владельцу: «положи `<CREDS_FILE>` в корень с полями url/email/password». Не выдумывай креды.

## Доступ 1 — вход через Playwright

Логин-форма: поля email/пароль, чекбокс «Запомнить меня» (если есть — оставь включённым), кнопка входа. Landing после входа зависит от роли (обычный пользователь и админ приземляются на разные разделы). Уточни селекторы полей из `browser_snapshot` — не угадывай.

**Поток (идемпотентный — не логинься, если уже залогинен):**

1. Прочитай креды из `<CREDS_FILE>`.
2. `browser_navigate` → `<APP_URL>` + landing-путь.
3. `browser_snapshot`.
   - Видишь контент приложения (шапку/меню авторизованного) → **уже залогинен**, переходи к тесту. (Сессия «Запомнить меня» живёт в профиле `.playwright-mcp`, часто переживает перезапуск.)
   - Редирект на `/login` → продолжай к шагу 4.
4. Заполни форму: `browser_type` email → `email`; `browser_type` пароль → `password` (refs бери из snapshot; можно `browser_fill_form`).
5. `browser_click` → кнопка входа.
6. `browser_wait_for` → текст/URL landing-раздела. Тост «Неверный логин или пароль» = проверь креды в файле, не угадывай.
7. `browser_take_screenshot` для фиксации, если нужна приёмка.

### Карта разделов (составь один раз в начале сессии)

Пройди меню авторизованного аккаунта и зафиксируй карту — она экономит клики и держит обход полным:

| Раздел | Путь | Роль приёмки |
|---|---|---|
| `<SECTION_MAIN>` | `/` | сводка/первый экран |
| `<SECTION_PRIMARY>` | `<PATH>` | **основной раздел приёмки** |
| `<SECTION_...>` | `<PATH>` | ... |
| `<ADMIN_SECTION>` | `/admin` | **только** под админ-аккаунтом, тестовому юзеру недоступен |

Отметь: какие разделы видит тестовая роль ({{PERSONAS}} — у разных ролей разное меню), где переключатель тенанта/организации (если мультитенант), где выход из аккаунта.

## Доступ 2 — «в базу»: `<DIAG_CMD>` (read-only, ПРОД/стенд)

Когда нужно понять, что реально произошло с сущностью на бэке (а не только как это выглядит в UI) — используй `<DIAG_CMD>`. Это **только чтение** (единственный не-GET — логин). Ходит на живую среду, логинится сервис-аккаунтом из `<DIAG_ENV_PREFIX>_*` в корневом env-файле (его читает сам рантайм через env-file, тебе эти креды видеть не нужно).

> 🔒 **Правило безопасности:** диагностика читает прод-данные всех владельцев/тенантов под сервис-аккаунтом → перед запуском в КАЖДОЙ новой сессии нужно явное «да» владельца («можно в прод»). Оно не переносится между сессиями. Токены/куки — никогда в чат. (Это касается только `<DIAG_CMD>`; обычный Playwright-вход тестовым юзером отдельного подтверждения не требует — аккаунт для того и заведён.)

Канонический запуск (base URL задавай **явно** — дефолт в env может указывать на устаревшую/сломанную среду):

```bash
<DIAG_ENV_PREFIX>_API_BASE=<APP_URL> {{PKG_MANAGER}} run <DIAG_CMD> <команда> [--флаги] [--json]
```

Набор команд (пример типовой read-only диагностики сущности):

| Команда | Назначение |
|---|---|
| `list --status <s> --limit N` | список сущностей (найти id тестовой) |
| `trace --<entity> <id>` | полная цепочка по сущности: состояние → шаги обработки → результат → логи |
| `result --<entity> <id>` | готовый результат обработки |
| `calls --<entity> <id>` | все внешние вызовы (провайдер, статус) |
| `call <callId>` | один вызов целиком (вход + ответ) |
| `chain --trace <traceId>` | технический след логов по traceId |
| `logs --at-least WARN --from <дата>` | прод-логи уровня ≥ WARN |

**Цикл приёмки UI ↔ данные:** нашёл/провёл тест-сценарий в UI → `<DIAG_CMD> list --limit 5` (взять id) → `<DIAG_CMD> trace --<entity> <id>` (увидеть, отработал ли конвейер) → `<DIAG_CMD> result --<entity> <id>` (сверить результат с тем, что в UI).

## Что проверять (чеклист приёмки)

Подстраивай под задачу, но базовый обход:

- **Вход:** логин проходит, приземление на нужный раздел, шапка/имя аккаунта видны.
- **Основной список:** грузится без ошибок, карточки/строки кликабельны, статусы корректны.
- **Целевая фича:** открывается сразу, поля соответствуют сценарию; действия (копировать / скачать / сохранить) работают; нет вечного «загрузка…» без объяснения.
- **Медиа / тяжёлый контент:** проигрывается/рендерится (если есть), не висит.
- **Разделы карты:** открываются, нет пустых/битых состояний; тексты соответствуют русский (нет чужого языка в UI, если продукт одноязычный).
- **Консоль:** `browser_console_messages` — нет красных ошибок на ключевых экранах.
- **Сеть:** `browser_network_requests` — нет 4xx/5xx на ключевых действиях.
- **Сверка с бэком:** при сомнении — `<DIAG_CMD>` (trace/result) по id сущности.

Найден баг → зафиксируй: что делал (шаги), что ждал, что получил, скриншот, если есть — id сущности и вывод `<DIAG_CMD> trace`.

## Артефакты и гигиена

- Скриншоты важной приёмки — в `plans/analysis/<тема>/`; временный мусор в корне допустим (если он gitignored по маскам), но не коммить его.
- **Никогда не коммить** `<CREDS_FILE>` и не делай `git add .` / `-A`.
- Креды и токены — не в чат, не в файлы под git.
- Тестируешь на живой среде: не плоди мусорные сущности без нужды, прибирай за собой только то, что создал сам, и только с подтверждения, если действие необратимо.

## TL;DR

1. Read `<CREDS_FILE>`.
2. Playwright: `navigate <APP_URL>` → если `/login`, заполни email/пароль → кнопка входа → ждём landing-раздел.
3. Тестируй по чеклисту, делай скриншоты.
4. Нужны данные с бэка → `<DIAG_CMD>` (read-only прод, спроси «можно в прод» один раз за сессию).
