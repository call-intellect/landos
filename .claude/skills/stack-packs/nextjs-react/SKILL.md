# {{PROJECT_NAME}}: стандарты фронтенда (React/Next.js)

> **OPTIONAL stack-pack.** Этот файл — эталонный пак под React/Next.js. Если фронтенд проекта на другом стеке — удали этот пак или замени аналогичным. Плейсхолдеры `{{...}}` заполняются под конкретный проект (стек, роли, язык интерфейса).

## Архитектура данных

### Три слоя, строго по порядку

```
API (backend) → ApiDto → DomainModel → UiModel → Компонент
```

| Слой | Что это | Пример |
|------|---------|--------|
| `ApiDto` | Сырые данные от бэкенда (snake_case, числа-строки, nullable) | `{ owner_id: "uuid", created_at: "2026-05-06T...", scheduled_at: null }` |
| `DomainModel` | Типизированная доменная модель (camelCase, Date, enum) | `{ ownerId: string, createdAt: Date, scheduledAt: Date \| null }` |
| `UiModel` | Данные, готовые для отображения (строки, флаги, метки) | `{ ownerName: string, statusLabel: string, isActive: boolean }` |

Не передавай `ApiDto` напрямую в компонент. Не смешивай слои. Маппинг `ApiDto → DomainModel` живёт в `domain/`-слое, `DomainModel → UiModel` — рядом с компонентом или в его хуке.

### Единый apiClient

Все HTTP-запросы — только через единый `apiClient` (fetch-обёртка или axios instance с baseURL, interceptors, auth-токеном). Не создавай отдельные клиенты и не зови `fetch`/`axios` напрямую из компонентов.

### Единый формат ошибок

```typescript
interface ApiError {
  message: string;
  code?: string;
  statusCode: number;
}
```

Нормализуй ошибки в одном месте (interceptor / общий обработчик клиента), не в каждом компоненте отдельно.

## Секреты и токены

- Никаких API-ключей, секретов или подписей внешних сервисов во фронт-коде, env-переменных фронта или бандле.
- Токены доступа к внешним сервисам ({{STACK_TERMS}}) выдаёт **только backend**, фронт их получает по запросу, не генерирует и не хардкодит.
- Всё, что попадает в клиентский бандл, считай публичным. Секрет во фронте = утёкший секрет.

## Архитектура компонентов

### Разделение ответственности

| Тип | Что делает |
|-----|-----------|
| Page-компонент | Роутинг, layout, оркестрация дочерних |
| Container-компонент | Получение данных, state management |
| UI-компонент | Только рендер, получает всё через props |

Бизнес-логика — в хуках, не в компонентах.

### Server state vs UI state

- **Server state** (данные с бэкенда) → через React Query / SWR / кастомные хуки с fetching
- **UI state** (открыт ли модал, текущий шаг формы) → useState / useReducer

Не клади server state в localStorage или глобальный контекст без необходимости — источник правды для серверных данных остаётся на сервере, фронт кэширует через data-fetching слой.

## UX-состояния (обязательные)

Каждый компонент, работающий с данными, обрабатывает все четыре состояния:

```tsx
if (isLoading) return <Skeleton />;
if (error) return <ErrorState message={error.message} onRetry={refetch} />;
if (!data || data.length === 0) return <EmptyState />;
return <DataView data={data} />;
```

Не оставляй пустой экран вместо loading state. Не показывай сырую ошибку пользователю. Empty-состояние — это отдельный осознанный экран, а не «данных нет, значит ничего».

Если у фичи есть свои значимые под-состояния (например, поток с несколькими фазами) — они моделируются явно и не замалчиваются.

## Авторизация и роли

### Провайдеры (порядок обёртки)

```
AuthProvider → ThemeProvider → NotificationProvider → Router
```

Порядок важен: нижние провайдеры видят контекст верхних. Auth — самый внешний, роутер — самый внутренний.

### Защита маршрутов — guard-компоненты

Доступ по ролям ({{PERSONAS}}) закрывается **guard-компонентами**, а не ручной проверкой роли внутри страницы:

| Компонент | Когда использовать |
|-----------|-------------------|
| `ProtectedRoute` | Любой маршрут, требующий авторизации |
| `RoleRoute` | Маршрут под конкретную роль/набор ролей |
| `AdminRoute` | Только для админ-раздела |

Не проверяй роль вручную (`if (user.role === ...)`) в теле компонента — используй guard-обёртку. Это единая точка правды о доступе и одинаковый редирект/фолбэк на всех страницах.

### Правила доступа

- Проверяй роль перед рендером action-кнопок (мутирующие действия, управление другими пользователями и т.п.).
- Скрывай UI-элементы недоступных операций (не только блокируй `disabled`).
- При попытке недозволенного действия — объясняй причину, не просто молчаливый fail.

## Формы

- Все формы — через React Hook Form + Zod.
- Схема валидации — отдельный файл рядом с формой.
- Submit — всегда через `handleSubmit`, с обработкой ошибок сервера (серверная ошибка мапится на поля/общий блок формы).
- Кнопка submit в состоянии `disabled`, пока форма отправляется.

---

## Стили

- Значения — из дизайн-токенов (CSS-переменные / токены темы), не из магических констант.
- Не хардкодить цвета, отступы, радиусы, тени — только токены.
- Не использовать inline styles для layout (только для действительно динамических значений).

## Язык интерфейса

**Весь user-facing текст — на русский.** Это касается label, placeholder, button, toast, breadcrumb, header, ошибок для пользователя, email-шаблонов, текстов внутри карточек/баннеров.

Если технический термин без оригинала теряет смысл и есть в речи команды (`SLA`, `feature flag`, `production` и т.п.) — оригинал можно оставить, но при первом упоминании на странице давать эквивалент на русский в скобках.

**Исключение** (НЕ переводить): технические идентификаторы, которые ровно так лежат в БД/коде/конфиге — env-имена, slug'и, поля JSON-payload, SQL-имена, ключи в реестрах, типы событий в логах. Их перевод сломает поиск/маппинг и запутает разработчика.

Не пускай в видимый UI текст без эквивалента на русский — даже «черновиком». Тестировщик и пользователь увидят ровно эту строку.

## SSR / рендеринг

SSR/SSG работает для публичных маршрутов (`/`, `/blog`, `/about` и подобных). Авторизованные и приватные разделы (кабинет, admin) — **не рендерятся на сервере**.

Не добавляй SSR-зависимые вещи (`window`, `document`, браузерные-only SDK) без проверки `typeof window !== 'undefined'` или изоляции в client-only компонентах.
