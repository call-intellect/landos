# Prisma: правила схемы, миграций и seeds

> **OPTIONAL stack-pack.** Включай, только если проект использует Prisma ORM.
> Правила seed / patch / sync-скриптов вынесены в [seed.md](seed.md).

> **Почему файловые миграции, а не `db push`.** Ad-hoc `prisma db push` на общей/прод-БД
> даёт частичные и дрейфующие состояния схемы при сбоях (осиротевшие enum, недостающие
> колонки → рантайм-ошибки на записи/чтении). Версионируемые файловые миграции делают
> каждое изменение явным, ревьюемым и идемпотентно применимым.

## Главное правило

> **ЛЮБОЕ изменение в БД = файл миграции.** Нет миграции — нет изменения. Точка.
> Никаких «по-быстрому через `db push` на проде». Каждая правка схемы коммитится миграцией.

**Источник истины о схеме — файлы `prisma/migrations/`** (плюс `schema.prisma` как desired-state).

- Изменение схемы → **`prisma migrate dev`** генерит файл миграции → ревью SQL → коммит.
- На прод/staging схема применяется **`prisma migrate deploy`** (только новые миграции, транзакционно) — **автоматически в деплой-хуке / CI**, а не руками. Деплой hands-free.
- `prisma db push` — **ТОЛЬКО** для быстрых черновых локальных экспериментов, которые **НЕ коммитятся**. Перед коммитом такой эксперимент оформляется нормальной миграцией через `migrate dev`.

> Пути ниже — относительно корня Prisma-приложения. В монорепо это может быть `<app>/prisma/`.
> Команды запускай через раннер проекта ({{PKG_MANAGER}} run …, обёрнутые в package.json-скрипты).

---

## Что НЕЛЬЗЯ делать

```bash
prisma db push                 # только локальный черновик, результат НЕ коммитить
prisma migrate reset           # на проде — никогда (дропает БД); локально — осознанно
```

Уже применённые миграции **не редактируются руками** — `prisma/migrations/<applied>/migration.sql`
считается неизменяемым. Нужна правка → новая миграция поверх.

---

## Что НУЖНО делать

```bash
prisma migrate dev --name <короткое_описание>   # создать миграцию из diff schema.prisma (генерит файл + применяет локально)
prisma migrate deploy                           # применить накопленные миграции (прод/CI; идемпотентно, транзакционно)
prisma migrate status                           # какие миграции применены, есть ли дрейф
prisma generate                                 # обновить Prisma Client (migrate dev делает это сам)
prisma db push                                  # черновой локальный эксперимент — результат НЕ коммитить
```

> В контейнеризованном проде `migrate deploy` зашивается в деплой-хук (шаг, идущий до старта
> приложения), а не выполняется вручную по SSH.

## Workflow изменения схемы

1. **Редактируй `prisma/schema.prisma`** (модель / enum / индекс / связь).
2. **Сгенерируй миграцию:** `prisma migrate dev --name add_x_to_y`.
   - Prisma создаст `prisma/migrations/<timestamp>_add_x_to_y/migration.sql`, применит к локальной БД и обновит Client.
   - Shadow-БД создаётся автоматически. Если роль без прав `CREATE DATABASE` — задать `shadowDatabaseUrl`.
3. **Отревьюй сгенерированный `migration.sql`** — особенно деструктив (DROP / ALTER TYPE / NOT NULL). Деструктивные шаги видны и проходят ревью именно здесь.
4. **Обнови связанный код** (см. таблицу ниже).
5. **Проверь:** `{{TYPECHECK_CMD}}`.
6. **Закоммить** миграцию вместе с кодом: `prisma/migrations/**` + `schema.prisma`.

| Что | Где |
|-----|-----|
| Миграция | `prisma/migrations/<ts>_<name>/migration.sql` (коммитить!) |
| Типы запросов / DTO / контракты | слой валидации вашего backend |
| Код доступа к данным | репозиторий / сервис соответствующего модуля |
| Клиентские типы API | слой API на фронте (если поле выходит наружу) |
| Документация модели данных | `second-brain/` — обновить описание модели данных |

## Baseline существующей БД (одноразово)

> Если в проде baseline автоматизирован деплой-хуком — команды ниже нужны для понимания
> механики и для локальных/ручных случаев.

Если БД уже существует (создана старым `db push`) и не имеет `_prisma_migrations`:

```bash
# 1. init-миграция из текущей схемы
prisma migrate diff --from-empty --to-schema-datamodel prisma/schema.prisma --script > prisma/migrations/0_init/migration.sql

# 2. привести БД к schema.prisma, если есть дрейф (reconcile, без db push):
prisma migrate diff --from-url "$DATABASE_URL" --to-schema-datamodel prisma/schema.prisma --script > reconcile.sql
# отревьюить reconcile.sql → применить его к БД вручную

# 3. пометить init применённой (НЕ выполняя SQL — БД уже в этом состоянии):
prisma migrate resolve --applied 0_init
```

После baseline — обычный цикл `migrate dev` (локально) / `migrate deploy` (прод).

> Флаги `migrate diff` менялись между мажорами Prisma. Сверь актуальные имена флагов
> (`--from-empty` / `--from-url` / `--to-schema-datamodel` и т.п.) через context7 для своей версии Prisma.

## Правила именования

| Сущность | Конвенция | Пример |
|----------|-----------|--------|
| Таблица (model) | PascalCase | `InvoiceLine` |
| Поле | camelCase | `ownerId`, `scheduledAt` |
| Enum | PascalCase | `PaymentStatus` |
| Enum value | как принято в проекте (snake_case / UPPER) | `not_started`, `ready` |
| Индекс | `@@index([field])` | `@@index([ownerId, status])` |
| Unique | `@@unique([...])` | `@@unique([tenantId, externalId])` |

## Безопасные vs деструктивные изменения

### Безопасные (без потери данных)
- Добавить новое поле с default / опциональное (`String?`)
- Добавить индекс / новую модель / новое значение в enum (в конец)

### Деструктивные (требуют осторожности — теперь видны в файле миграции)
- Удалить / переименовать поле, изменить тип, удалить значение enum, сделать поле обязательным

Для деструктивных:
1. Убедись, что нет prod-данных, которые сломаются.
2. Если есть — **сначала data-миграция** (patch-скрипт, см. [seed.md](seed.md)), **потом** миграция схемы.
3. Перед деструктивным `migrate deploy` на проде — бэкап (`pg_dump`).
