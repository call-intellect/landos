# Production review gate

Это **единый канон ревью** шаблона. Любой code review — через этот скилл. Не плоди параллельные ревью-**процессы** (второй чек-лист, свой порядок проверок, другой формат вердикта) — канон один. Это НЕ запрет на суб-агента: запустить этот же скилл в отдельном агенте — не второй процесс, а тот же канон в чистом контексте.

## Ревьюер ≠ автор (жёсткое правило)

**Писал этот код ты или твой суб-агент — ревьюй свежим контекстом**, отдельным агентом, которому на вход идут только дифф и критерии. Причина механическая, а не про «предвзятость»: в контексте автора на входе у тебя не дифф, а собственные рассуждения о том, почему дифф верен, — и ты оценишь намерение вместо факта. Это то же правило, по которому оркестратор не верит отчёту агента и перечитывает код глазами; здесь оно применяется к тебе самому.

Ревьюишь сам (нет `Agent`, тривиальный дифф, ты уже запущен суб-агентом) — **скажи это в вердикте**: «ревью в контексте автора, независимой проверки не было». Одного свежего ревьюера достаточно: независимость контекста и есть весь эффект. Веер по осям ниже — не нужен: ревьюер, посланный искать дыры, найдёт их и в здоровом коде, и N ревьюеров дадут N порций ложных тревог — против чего и стоит правило «докажи, что баг реальный».

## Главное правило: докажи, что баг реальный (не false-positive)

Каждый CRITICAL/MEDIUM finding обязан быть **доказан**, а не заподозрен. Это работа **прохода 2** (см. ниже): на проходе 1 подозрение записывается как есть, а здесь оно либо доказывается, либо снимается. Перед тем как вынести находку в вердикт:

1. **Прочитай реальный код по точным путям** (`RepoBrain` для навигации; если есть кодовый индекс — зови его первым, затем открывай нужные строки на чтение). Не выводи баг из имени функции или догадки о том, «как обычно бывает».
2. **Построй конкретный сценарий отказа**: какие вход/состояние → какое неверное поведение/сбой. Если сценарий не строится — это не находка.
3. **Проверь, не закрыт ли риск выше по стеку** (guard, валидация DTO, транзакция, обёртка-ретрай, инвариант на уровне БД). Множество «багов» уже нейтрализованы на границе — такой finding снимается.
4. Не уверен, что баг реальный, но риск серьёзный → выноси в раздел **Edge cases to verify** (гипотеза для ручной проверки), НЕ в Critical.

## Два прохода: сначала перечисли, потом фильтруй

**Проход 1 — перечисли всё.** Пройди 10 категорий сверху вниз и выпиши **каждое** подозрение, ничего не отсеивая: на этом проходе фильтр запрещён. Порог «сообщать или нет» здесь не применяется — он применяется в проходе 2.

**Проход 2 — докажи или сними.** По каждому пункту прохода 1: прочитай реальный код по точным путям, построй сценарий отказа, проверь, не закрыт ли риск выше по стеку. Доказано → Critical/Medium. Не доказано, но риск серьёзный → Edge cases to verify. Сценарий не строится → снято.

Порядок именно такой, потому что фильтр на входе стоит дороже фильтра на выходе: не выписанное подозрение уже не вернуть, а лишнее снимается проходом 2 за минуту.

## Порядок проверки (строго сверху вниз)

Категории идут от критического к минорному — это маршрут прохода 1. Не переходи к следующей, пока не завершил предыдущую.

### 1. Production-breaking logic bugs
- Логика, которая приведёт к неверному поведению в production прямо сейчас
- Race conditions, неверные условия, инвертированная логика, off-by-one
- Ошибки в доменном конечном автомате: переход в недопустимое состояние, обход инварианта, возврат из терминального состояния в активное (конкретные автоматы и запрещённые переходы — см. `{{DOMAIN_HIGH_IMPACT}}`)

### 2. Auth и access control
- Отсутствие проверки роли/ownership перед мутацией данных
- Эндпоинты без guard'ов / без проверки аутентификации
- **Внешний клиент/гость не должен получать секреты инфраструктуры** (API key/secret, ключи подписи) — только короткоживущий scoped-токен с минимальными правами
- Токен одного субъекта не должен давать доступ к ресурсам другого (горизонтальная эскалация)
- Отсутствие проверки owner-ключей (`userId`/`ownerId`/`tenantId`/`resourceId`) в запросах — риск IDOR
- Пропуск tenant-скоупинга в multi-tenant запросе (данные чужого арендатора)

### 3. Data corruption / data loss risks
- Операции без транзакций там, где нужна атомарность (частичная запись оставит систему в неконсистентном состоянии)
- Cascading deletes без явного намерения (родитель → дочерние сущности удаляются молча)
- Overwrite данных без проверки существующего значения / без optimistic-locking (потерянное обновление)
- Отсутствие soft delete / аудита там, где данные восстанавливать критично
- Удаление данных без учёта retention-политики ({{PROJECT_CONSTRAINTS}})

### 4. Incorrect state transitions
- Переходы конечного автомата не через явный state machine, а «прямой записью поля»
- Возможность перейти в недопустимое состояние напрямую через API, минуя валидацию перехода
- Отсутствие проверки current state перед transition
- Статусы внешних/асинхронных задач (started / ended / failed / cancelled) обрабатываются непоследовательно — часть путей не покрыта

### 5. Payment, billing, quota, retention risks
- Двойное списание / двойное начисление
- Отсутствие idempotency key при платёжных/денежных операциях
- Metered-биллинг (по объёму/времени) считается дважды при retry
- Лимит/квота/retention не соответствует тарифу или заданному владельцем параметру ({{PROJECT_CONSTRAINTS}})
- Списание/блокировка средств без явного владельческого решения

### 6. Integration retry и idempotency
- Внешние вызовы ({{STACK_TERMS}}: сторонние API, хранилище, очереди, email/уведомления) без retry-логики или без таймаута
- Webhook от внешней системы обрабатывается без проверки «уже обработали» (нет dedup по event id)
- Операции, которые при повторном вызове создадут дублирование сущностей/эффектов
- Фоновые задачи/jobs без проверки «уже выполнено» (at-least-once доставка требует идемпотентного обработчика)

### 7. Missing validation
- Отсутствие валидации на уровне DTO/входной схемы
- Поля, которые могут прийти `undefined`/`null`/пустыми и сломать нижележащую логику
- Отсутствие проверки business rules (границы, лимиты, обязательные предусловия — см. {{PROJECT_CONSTRAINTS}})
- Доверие к клиентскому вводу для чувствительных полей (цена, роль, флаги, id владельца)

### 8. Observability и logging gaps
- Критические операции без логирования через централизованный логгер проекта
- Обработчики webhooks/внешних событий без trace-контекста
- Дорогие/внешние вызовы без трейсинга (input/output/latency/cost)
- Ошибки, которые проглатываются (`catch {}` без re-throw/лога) и исчезнут бесследно

### 9. UX states, которые trap users
- Пользователь попадает в состояние, из которого нет выхода (экран навсегда завис в loading/connecting)
- Отсутствие empty state, error state, loading state
- Action-кнопка, которая при определённых условиях молча ничего не делает (без объяснения / без disabled-состояния)
- Битая ссылка/невалидный ресурс отдаёт голый 500 вместо понятной страницы

### 10. Style и cleanup
- Только после всего выше
- Неиспользуемые imports, отладочные `console.log`/print, закомментированный код
- Нарушения code style проекта

## Формат вывода

### Структура ответа

```
## Critical issues
- [CRITICAL] <описание> — <file:line>
  Сценарий отказа: <вход/состояние → неверное поведение>
  Fix: <что именно исправить>

## Medium risks
- [MEDIUM] <описание> — <file:line>
  Сценарий отказа: <вход/состояние → неверное поведение>
  Fix: <что именно исправить>

## Minor issues
- [MINOR] <описание>

## Edge cases to verify
- <сценарий/гипотеза, которую стоит проверить вручную>

## Merge verdict
BLOCK / APPROVE WITH FIXES / APPROVE
Reason: <одна строка>

## Residual risks (если APPROVE / APPROVE WITH FIXES)
- <что осталось непроверенным или требует мониторинга после мержа>
```

### Вердикт
- **BLOCK** — есть хотя бы один доказанный CRITICAL, который сломает production.
- **APPROVE WITH FIXES** — CRITICAL нет; есть MEDIUM/MINOR, которые надо поправить, но не блокирующие.
- **APPROVE** — блокеров нет; допустимы Residual risks под мониторинг.

### Если findings нет

Явно написать: **"No critical findings."** — и перечислить, что именно было проверено, плюс указать residual risks / testing gaps. Пустой ответ без перечня проверенного — не результат ревью.
