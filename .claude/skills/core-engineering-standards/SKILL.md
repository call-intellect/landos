# Инженерные стандарты

## Перед тем как писать код

### Execution plan для нетривиальных задач

Для любой задачи, которая не решается за один очевидный шаг — сначала план, потом код.

Execution plan — это короткий список шагов (3–7 пунктов) с указанием:
- Что именно меняется (файлы, модули, эндпоинты)
- В каком порядке
- Какие зависимости между шагами

Показывай план пользователю до начала реализации. Это позволяет поймать неверные предположения до того, как они превратятся в код.

### Минимальные безопасные изменения

Предпочитай изменения, которые:
- Меняют только то, что требует задача
- Не трогают рабочую бизнес-логику без явной необходимости
- Не переписывают модуль целиком ради одного исправления

Широкий рефакторинг без задачи — красный флаг. Если видишь что-то «плохое» рядом — зафиксируй в `second-brain/`, но не трогай без согласования.

### Явные предположения

Если делаешь предположение о поведении системы, API, бизнес-логике — проговори его явно перед тем, как действовать. Скрытые предположения — главный источник трудноотлавливаемых багов.

### Фазовая работа для medium/large задач

Если задача затрагивает 3+ файла, несколько модулей, или требует изменения схемы БД — разбивай на фазы:

```
Фаза 1: [что делаем] — [почему именно это первым]
Фаза 2: [что делаем] — [зависит от фазы 1]
...
```

**Каждая фаза оставляет систему в рабочем состоянии** — компилируется, проходит проверку сборки, ничего не сломано наполовину. Не начинай следующую фазу, пока текущая не «зелёная».

## Лёгкая тропа — «сложность → маршрут»

Не каждая задача заслуживает полной цепочки планирования, и не каждая правка безопасна «сразу в код». Выбери маршрут по blast radius, а не по тому, «насколько мелкой она выглядит».

### Прямой маршрут (execution plan → код)

Иди напрямую, если выполнены **ВСЕ** условия:
- Правка укладывается в **1–2 файла**.
- Нет развилок «как лучше» — решение очевидно, разумный вариант ровно один.
- Не трогает публичные контракты API, схему БД, бизнес-инварианты, FSM, деньги/доступ.
- Не нужен рыночный/конкурентный ресёрч.
- Изменение обратимо и локально (малый радиус поражения).

Примеры: фикс бага в одной функции, добавление поля в уже существующий ответ, правка текста/валидации, локальный рефактор без смены поведения.

Для прямого маршрута всё равно составь короткий execution plan (даже 2–3 пункта) и проговори предположения — просто без полной цепочки скиллов.

### Средняя тропа (execution plan + фазовость)

3+ файла или несколько модулей, **но замысел ясен и нет развилок владельца** — оформи фазовый execution plan, согласуй, делай фазами (каждая оставляет систему рабочей). Полная цепочка не нужна. Если по ходу вскрывается развилка владельца или растёт blast radius → эскалируй в полную цепочку.

### Полная цепочка (feature-analyst → solution-blueprint → tz-author → tz-orchestrator)

Включай полную цепочку, если верно **ХОТЯ БЫ ОДНО**:
- 3+ файла И/ИЛИ новая подсистема / несколько модулей с нетривиальной связью.
- Есть развилка «как лучше» с ≥2 разумными вариантами → нужен доказательный выбор (**feature-analyst**).
- Меняется, что видят/могут люди, деньги или доступ → нужна архитектура человеческим языком, которую **владелец одобряет ДО ТЗ** (gate `approved` в **solution-blueprint**).
- Меняется схема БД / публичный контракт / FSM / межмодульные связи.
- Нужен рыночный или конкурентный анализ, сравнение решений.
- Изменение необратимо или имеет высокий blast radius.

| Признак задачи | Маршрут | Усилие |
|---|---|---|
| 1–2 файла, решение очевидно, локально и обратимо | Прямой (execution plan → код) | `low` / `medium` |
| 3+ файла, замысел ясен, развилок владельца нет | Средняя (фазовый execution plan) | `high` |
| Развилка «как лучше», деньги/доступ, схема/контракт, ресёрч, необратимость | Полная цепочка (analyst → blueprint → tz-author → orchestrator) | `xhigh` |

Ревью и стоп-кран отладки — тоже `xhigh`: там цена пропуска выше цены лишнего думанья.

**Усилие задаёт человек на старте сессии** — флагом CLI `--effort <low\|medium\|high\|xhigh\|max>` или через `/config`; суб-агентам оно передаётся параметром `effort` при запуске. В `.claude/settings.json` ключ `effort` **не добавляется**: подтверждён только флаг CLI, а настройку CLI молча глотает и заведомо несуществующую — «работает» там ничего не доказывает.

**Правило дефолта:** сомневаешься между тропами — бери более тяжёлую на один шаг. Текст (план/архитектура/ТЗ) дешевле переделки кода. Но и не раздувай тривиальную правку в полноценное ТЗ — это тоже потеря.

## Границы модулей — где резать

Тропа выше отвечает «сколько думать», этот раздел — «куда класть». Вопрос тот же самый и в тот же
момент: как только правка выходит за один файл, вы уже выбираете границу — молча или осознанно.

**Модуль прячет решение, которое вероятнее всего изменится** (Парнас, 1972), а не шаг работы и не
технический слой.

- **Режь по фичам и доменам, а не по слоям.** Хорошее имя модуля — существительное предметной
  области (`покупки`, `рассылки`, `доступ`). Плохое — технический уровень (`services`, `utils`,
  `helpers`, `common`). Проверяемый признак: при фичевой раскладке типичный коммит трогает **одну**
  папку, при слоёной — 3–5.
- **Когда НЕ резать.** Правило трёх для дублирования: по двум примерам обобщается случайное
  совпадение, ждите третьего. Интерфейс с единственной реализацией — не абстракция, а лишний
  прыжок при чтении. «Вынесем на будущее» — расход сегодня ради сценария, который может не
  наступить.
- **Единственная граница, которую проводят авансом, — обёртка над внешним миром** (платёж, почта,
  хранилище, очередь, провайдер модели). Исключение честное: вторая реализация у неё уже есть —
  это тестовая заглушка. Практически: SDK внешнего сервиса импортируется **из одного места**,
  остальной код зовёт вашу функцию.
- **Четыре проверки, что граница настоящая, а не нарисованная папкой:** (1) удаление — сколько
  чужих файлов покраснеет, если убрать модуль целиком; (2) описание одной фразой **без «и»**;
  (3) тест модуля без поднятия соседей; (4) зависимость односторонняя — цикл `A ↔ B` означает
  **один** модуль, разрезанный пополам, а не два.
- **Что заменяют в реальности:** внешние сервисы — да, регулярно; базу, ORM, фреймворк — почти
  никогда. Слой абстракции «чтобы когда-нибудь уйти с Postgres» не окупается.

Разбор с обоснованием, частые ошибки и как измерить это у себя — `references/module-boundaries.md`.

## Проверка сборки

### Package manager

Используй **пиннутый в проекте пакетный менеджер `{{PKG_MANAGER}}`** и не смешивай его с другими. Не подменяй его на «то, что под рукой» — lock-файл и рантайм-совместимость зависят от него.

### Команды проверки

| Что проверяем | Команда |
|---|---|
| Typecheck | `{{TYPECHECK_CMD}}` |
| Lint | `{{LINT_CMD}}` |
| Build (prod-like) | `{{BUILD_CMD}}` |
| Тесты | `{{TEST_CMD}}` |

В монорепо запускай проверку в затронутом пакете (или в обоих, если правка задела и backend, и frontend).

### Когда запускать

- Изменения в одном пакете → проверяй этот пакет.
- Изменения затрагивают несколько пакетов → проверяй все затронутые.

**Build-гейт: не сообщай о завершении задачи, если сборка красная.** «Готово» без зелёного билда — это не готово. Typecheck/lint/build/тесты по затронутой области — часть определения «сделано», а не опциональный финальный штрих.

## Работа с `second-brain` и `plans`

- Любая новая фича → план в `plans/` до начала работы.
- Изменение бизнес-логики → обновление `second-brain/`.
- Новый модуль/эндпоинт → заметка в `second-brain/01_projects/`.
- Изменение схемы БД → обновление профильной заметки о модели данных в `second-brain/`.

Typo, стили, рефакторинг без изменения логики — в `second-brain/` не фиксируются.

### Одноразовое — в `artifacts/`, корень чистый

Архивы, дампы, снимки экрана, черновики, временные скрипты, отчёты прогонов кладутся в `artifacts/`
(каталог в `.gitignore`), а не в корень репозитория. Корень — лицо проекта: там лежит только то, что
читатель должен увидеть первым.

- Нужен один раз (проверить гипотезу, показать владельцу, приложить к отчёту) → `artifacts/`.
- Нужен другим сессиям — у файла есть штатное место: знание → `second-brain/`, замысел → `plans/`, код → модуль.
- Сомневаешься — `artifacts/`: оттуда достать легко, из корня чужой мусор вычищают руками.

## Чеклист перед завершением задачи

- [ ] Маршрут выбран осознанно (прямой / средний / полная цепочка) — по blast radius, не по «ощущению мелкости»
- [ ] Execution plan был согласован (для нетривиальных задач)
- [ ] Изменения минимальны и не задевают лишнее
- [ ] Новый код лёг по границе фичи, а не слоя; внешний сервис зовётся из одного места
- [ ] Все предположения проговорены
- [ ] Каждая фаза оставляла систему рабочей
- [ ] Сборка зелёная (`{{TYPECHECK_CMD}}` · `{{LINT_CMD}}` · `{{BUILD_CMD}}` · `{{TEST_CMD}}` по затронутой области)
- [ ] `second-brain/` обновлён (если изменилась логика)
- [ ] План в `plans/` обновлён (фазы отмечены)
