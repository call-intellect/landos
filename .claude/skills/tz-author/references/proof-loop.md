# Второй проход по триггеру + challenge-loop

Цель — не «сделать дважды для галочки», а получить доказанное лучшее решение.

**Когда запускается проход B.** По триггеру, а не на каждое ТЗ: развилка с двумя и более сильными вариантами · необратимое решение · затронуты деньги, доступ, данные или схема. Ни один триггер не сработал — одно решение и честная строка в ТЗ: «второй проход не запускался, развилки не было». Challenge-loop прогоняется **всегда**: он стоит абзац, а не суб-агента.

**Проход B — отдельным суб-агентом.** В твоём контексте настоящей независимости не бывает: он не стирается между проходами, ты уже видел A и будешь бессознательно защищать его (self-preference). Суб-агент даёт независимость физически — другой контекст. Это тот же приём, которым `feature-analyst` ставит red-team (`../../feature-analyst/references/fanout-playbook.md`), и здесь он нужен ровно за тем же. Промпт B **самодостаточен и не содержит решения A** — только задача, ограничения фичи и точки в коде; иначе это не независимый проход, а эхо.

Нет `Agent`/`Workflow` (headless / ты сам суб-агент) → делай B в своём контексте: «независимость» деградирует до **принудительной генерации архитектурно иного варианта** (а не самообмана «забудь A»), и в ТЗ **честно пометь**: «проход B — в одном контексте, независимость ограничена».

## Проход A — от кода
Лучшее решение из контекста Шага 1: как лечь в текущую архитектуру, переиспользуя существующие воркеры/сервисы/промпты/DTO. Минимум новых сущностей.

## Проход B — от best-practice (суб-агент с независимым retrieval)
Принципиально другой подход. Источники ищи **своими стартовыми запросами**, не переиспользуй выдачу прохода A: context7 (актуальный API либы), WebSearch (отраслевой паттерн), альтернативная архитектура. Формулируй честно — не как соломенное чучело, которое легко побить.

**Ось различия (обязательна).** B засчитан, только если отличается от A хотя бы по одной оси:
- **Модель данных** — новая таблица vs расширение существующей vs денормализация.
- **Точка интеграции** — в существующем модуле vs новый модуль vs внешний сервис.
- **Синхронность** — синхронно в запросе vs очередь vs периодический cron.
- **Провайдер/механизм** — другой tier/провайдер, другой стор, другой алгоритм.

Если различие только косметическое (переименование, та же архитектура) — проход B **не засчитан**, генерируй заново.

## Сведение — состязательная таблица
4–7 критериев = реальные ограничения фичи (нагрузка, tenant-изоляция, стоимость внешнего вызова, идемпотентность, обратная совместимость, сложность поддержки, time-to-ship).

| Критерий | A (от кода) | B (best-practice) |
|---|---|---|
| Стоимость/мес | ✓ дёшево (дешёвый tier) | ✗ дорого (дорогой tier на каждый вызов) |
| Идемпотентность | ✗ нужна доработка | ✓ из коробки (идемпотентный ключ) |
| … | … | … |

Или формат отвергнутых альтернатив:
| Альтернатива | На чём ломается |
|---|---|
| Синхронно в HTTP-запросе | таймаут на >100 элементов, урок нагрузки |

- **Сошлись** (оба указывают на одно) → высокая уверенность, фиксируй.
- **Разошлись, оба сильны** → это HIGH-impact развилка → вопрос владельцу (`clarifying-questions.md`), не решай молча.

## Challenge-loop — 3 вопроса к выбранному решению
1. **Корень, не симптом?** Один симптом ≠ один корень. Чини весь КЛАСС (все вхождения паттерна через impact-graph), а не один кейс. Обратная сторона: один симптом может иметь несколько корней — верифицируй каждый отдельно.
2. **Самое эффективное?** Нет ли проще/дешевле? Не преждевременная ли оптимизация под несуществующую нагрузку — если да, отложи с **числовым** триггером («ввести шардинг при >1M строк»), а не «на всякий случай».
3. **Нет ли кода ради кода?** Мёртвый задел, дублирование вместо переиспользования. Задел — либо подключить сейчас, либо удалить (типовой урок: висящий неподключённый промпт/сервис).

**Перепиши решение** по итогам. Существенно переписал → прогони loop ещё раз. Нумеруй решения Б1…Бn, у каждого колонка «Обоснование (Почему)» + ссылка на правило/память. Ни одного решения без «почему».

## Мини-e2e проверка поведения (когда факт спорный)
Доки (context7) описывают API, но не поведение. В спорных местах докажи эмпирически и впиши в ТЗ как факт:
- Scope middleware/guard'ов фреймворка, порядок обработчиков, `req.url` vs `originalUrl`.
- Кварки внешнего API (формат ответа провайдера, лимиты, кэш-поведение).
- Бинарные форматы (атомы/заголовки медиа, faststart), сигнатуры из исходников зависимости.
Минимальный спек за минуту > интуиция.

## Антипаттерны
- Два прохода прозой без таблицы и без оси различия → не считается.
- «B хуже, потому что я уже выбрал A» → предвзятое сведение, переформулируй B честно.
- Состязательная таблица с критериями, не относящимися к ограничениям фичи → вода.
