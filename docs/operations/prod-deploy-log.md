## 📌 Инварианты выката (обязательны, не переписывать под конкретный push)

1. **Один вход исполнения.** Все команды этого файла — через `{{RUNTIME_EXEC}} <script>`. Никаких прямых `cd … && {{PKG_MANAGER}} run …` вразнобой: единый вход = единая среда, меньше «у меня локально иначе».
2. **Release-тег на каждый выкат.** Каждый реальный выкат получает git-тег (например `deploy-YYYY-MM-DD-N`), **привязанный к точному git SHA**, и строку в этом журнале (дата · SHA · кто выкатил). Это даёт трассируемость «ошибка в проде → какой релиз её принёс» (стиль трекеров ошибок: у каждого события — release-маркер).
3. **Пустой шаг НЕ удаляем.** Если шаг не затронут этим выкатом — оставляй рубрику и помечай `N/A — не затронуто` или `⚠️ WARNING — <причина, почему пропущен>`. Молча удалённый шаг читается как «забыли», а не «сознательно пропустили» (стиль run-book: каждый пункт явно закрыт).
4. **Бэкап перед необратимым.** Любая миграция / patch, меняющие данные, идут только после бэкапа (Шаг 0).

## 🔄 Правила поддержки файла

### Жёсткие правила формата команд

1. **Все команды — через единый вход** `{{RUNTIME_EXEC}} <script>`. Никаких разрозненных `cd … && run` на хосте.
2. **patch/seed/backfill/migrate-скрипты** — `{{RUNTIME_EXEC}} <script>` (сервис запущен) ИЛИ разовый контейнер/процесс (если сервис ещё не стартовал — например, в Шаге 3).
3. **Схема/индексы** — автоматически на старте деплоя; вручную — отдельной командой через `{{RUNTIME_EXEC}}`.
4. **Бэкап БД** — только через `{{RUNTIME_EXEC}}`, не локальными клиентами к IP сервера.
5. **ENV** — правка прод-конфига + рестарт с пересозданием контейнера/процесса.
6. **Рестарт** — rebuild (новый код) либо force-recreate (новый ENV).

### Когда обновлять

После каждого `git push` в `main`, если push содержит:

| Что изменилось | Куда писать в «Накоплено к выкату» |
|---|---|
| Схема БД (новая модель / nullable→NOT NULL / drop / новый enum) | Шаг 4 |
| Индексы / init вне схемы | Шаг 5 |
| Новый `patch-*` | Шаг 6 |
| Новый `seed-*` | Шаг 7 |
| Новый `backfill-*` | Шаг 8 |
| Новый `migrate-*` | Шаг 9 |
| Новый `setup-*` (per-tenant) | Шаг 10 |
| Новая ENV в схеме конфига | Шаг 1 |
| Новый worker / cron / очередь | Шаг 12 (smoke: grep по наличию) |
| Новый REST/OpenAPI раздел | Шаг 12 (smoke: раздел виден) |
| Включение нового флага по умолчанию | Шаг 1 + строка в `feature-flags.md` |
| Изменения в манифесте оркестрации (сервисы / порты / зависимости) | Шаг 0 или Шаг 11 |
| Изменения в Dockerfile / lockfile | Шаг 2 |

### Как обновлять

1. После `git push` запусти:
   ```bash
   git show --stat HEAD
   git diff HEAD~N --name-only
   ```
2. Для каждого затронутого файла добавь строку в соответствующий Шаг — **обязательно** с префиксом `{{RUNTIME_EXEC}} …`.
3. Переименовал/изменил поведение существующего скрипта — **обнови запись inline**, не дублируй.
4. Запись стала неактуальной (фича откатилась) — удали её из «Накоплено к выкату».
5. Незатронутый шаг **не удаляй** — помечай `N/A` или `WARNING` с причиной.

### Когда переносить в архив

После триггера «выкат прошёл / прод обновили / выкатили» — целиком копируешь блок «🚨 Накоплено к выкату» в новый подраздел `## 📂 Архив применённых` → `### YYYY-MM-DD — выкат N` с указанием git SHA, release-тега, кто выкатил и какие были инциденты. Раздел «Накоплено к выкату» обнуляется (пустые Шаги 1–12).

### Связь с рефлексией / журналом разработки

При записи рефлексии всегда **ссылайся** на этот файл вместо дублирования команд («prod-инструкция обновлена → см. `docs/operations/prod-deploy-log.md`»).
