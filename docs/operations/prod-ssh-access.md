## 🔒 ПРАВИЛО №1 — каждый прогон на проде согласовывать с владельцем

Любая команда на прод-сервере требует **явного «да» владельца в текущей сессии** под конкретную команду. Общее «добро» на доступ ≠ разрешение на конкретный прогон. Перед каждым прогоном:
1. Показать владельцу точную команду, которую собираешься выполнить.
2. Дождаться подтверждения.
3. Только потом выполнять. Вывод (без секретов) — обратно в чат.

Это правило-близнец к «прод-диагностика только с явным да» — но строже: доступ на проде даёт запись/выполнение, а не только чтение.

## Доступ — по SSH-ключу (дефолт)

Настройка доступа с нуля — скилл `server-access`. Пароль владельца агент не принимает
и не хранит; при верной настройке **секрета в проекте не существует**.

- Алиас: `{{SSH_ALIAS}}` → `{{PROD_HOST}}`, юзер `{{PROD_USER}}`.
- Приватный ключ: `~/.ssh/{{PROJECT_SLUG}}_prod` — вне репозитория, не коммитится, не показывается.
- Алиас прописан в `~/.ssh/config` (локальный файл, в git не едет).
- Вызов: `ssh {{SSH_ALIAS}} "<команда>"`. Проверка живости: `ssh -o BatchMode=yes {{SSH_ALIAS}} 'hostname'`.
- Путь проекта на сервере: `{{PROJECT_DIR}}`.

### Запасной путь — пароль (только если хостер не поддерживает ключи)

Деградация, а не альтернатива: пароль в файле лежит plaintext, а `sshpass` светит его
в `ps`. Применил — пометь строкой в реестре не-сделанного с причиной.

Реквизиты — в `/.prod-access.local.json` (gitignored). В этот файл (он в git) секреты
НЕ писать никогда. Формат:
```json
{
  "host": "{{PROD_HOST}}",
  "user": "{{PROD_USER}}",
  "password": "…",
  "projectDir": "…"
}
```
Если неинтерактивной авторизации нет вовсе — команду выполняет владелец и присылает вывод.

## 🧭 Список граблей окружения (заполняй, чтобы агент не переоткрывал)

<!--

Примеры категорий (замени на реальные для своего сервера):

1. **Неинтерактивный ввод пароля.** Опиши проверенный способ на машине агента (`sshpass` / `expect` / добавленный ключ). Если ни одного — прогон делает владелец.
2. **root напрямую.** Обычно root по SSH запрещён — заходить обычным `{{PROD_USER}}`, затем повышать права под конкретную команду.
3. **Локализованные промпты.** Промпт ввода пароля повышения прав может быть НЕ на английском — ловить оба варианта.
4. **Пейджеры вешают сессию.** `git log` / `psql` / список контейнеров под псевдо-tty открывают пейджер и ждут ввод → таймаут. Гони с отключённым пейджером (`GIT_PAGER=cat`, `-P pager=off`, `--format`).
5. **stdin у пайп-скриптов.** Скрипт, поданный в интерпретатор через пайп, читает stdin; вложенные интерактивные вызовы «съедают» остаток → обрыв. Перенаправляй `</dev/null` на каждый вложенный вызов или пиши во временный файл.
6. **Экранирование SQL/строк.** Не мучиться с кавычками — слать блок через base64 (`echo <b64> | base64 -d | bash`) с учётом п.5.
7. **Различия утилит хоста агента и прод-Linux.** Часть команд есть на удалённом Linux, но не на машине агента (или наоборот) — не оборачивай локально в то, чего нет.

## Когда вообще нужны ручные прогоны (это НЕ повседневность)

В нормальной работе ручные команды НЕ нужны — конвейер работает сам (воркеры + cron добивают по расписанию). Ручной прогон оправдан только в трёх случаях:
1. **Разовая миграция данных после деплоя**, меняющего, какие данные участвуют (backfill догоняет исторические данные ОДИН раз).
2. **Ускорение приёмки**: форснуть cron, чтобы не ждать ночного расписания во время теста. В реальной эксплуатации просто ждут.
3. **Точечная диагностика инцидента** (read-only: чтение логов / метрик / БД).

> Ловишь себя на «надо прогонять команду регулярно» — это сигнал, что чего-то не хватает в автоматике (cron/событие). Чинить кодом, а не превращать в ручной ритуал.

## Read-only по умолчанию

Для диагностики — **исключительно** чтение (`SELECT`, логи, метрики). Любой write / restart / deploy — только с отдельным явным «да» владельца под конкретную команду.

## Частые безопасные команды (выполнять по правилу №1)

<!-- Как заполнять: подставь свои реальные команды через {{RUNTIME_EXEC}}. Ниже — форма. -->

- Полный апдейт-выкат скриптов: `{{RUNTIME_EXEC}} <apply-all-script> --mode update`
- Форс cron (ускорить приёмку): `{{RUNTIME_EXEC}} <run-cron-script> <cron-name>`
- Backfill (разовый догон): `{{RUNTIME_EXEC}} <backfill-script> --tenant=<id>`
- Read-only диагностика БД: `{{RUNTIME_EXEC}} <db-read-only-query>`
