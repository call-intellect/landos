# Политика версий и релизов кита

Чтобы не резать новую версию кита на каждую правку. Одна версия = пачка изменений.

## Куда копятся правки

Каждое приземлённое изменение кита — строкой в [CHANGELOG.md](../../CHANGELOG.md),
раздел `## [Unreleased]`, сгруппировано: `Добавлено` / `Изменено` / `Исправлено`.
Одна правка = одна строка **языком пользователя** (что изменилось для того, кто ставит кит),
а не «поправил файл X». Строки копятся сколько угодно — день, неделя; релиз пока не режется.

## Когда режем релиз

Не по календарю и не на каждый чих. Триггер — **решение владельца**, ориентир:
накопилось **≈5+ заметных пользователю изменений** ИЛИ набралась цельная тема.
Обратная сторона тоже верна: если в `[Unreleased]` пара мелочей и давно тихо — можно
выкатить и их, чтобы правки не висели непоставленными неделями.

## Как режем релиз (3 шага)

1. В `CHANGELOG.md`: переименуй `## [Unreleased]` → `## [X.Y.Z] — ГГГГ-ММ-ДД`,
   заведи сверху новый пустой `## [Unreleased]`.
2. Обнови `tools/build-kit/VERSION` → `X.Y.Z`.
3. `bash tools/build-kit/build.sh` → новый `dist/vibeos-kit-X.Y.Z.tar.gz`.
   Витрина «что нового» магазина берёт текст из свежего раздела CHANGELOG.
4. Поставь тег на коммит релиза: `git tag -a vX.Y.Z -m "релиз X.Y.Z"` и запушь его
   (`git push origin vX.Y.Z`). Шаг заведён 28.07.2026: до 0.8.0 тегов не было ни у одного релиза,
   и вопрос «какой именно состав уехал клиенту в 0.7.1» восстанавливался только по датам коммитов.

Никогда не пересобирай тарбол под **тем же** номером с другим содержимым: `0.5.0` у клиента
и `0.5.0` в `dist/` обязаны совпадать побайтно. Изменилось содержимое → изменился номер.

## Номер версии (кит на 0.x)

Вопрос-решатель: **получает ли пользователь новую способность, которую он осознанно осваивает?**

- **Да, новая способность / меняется то, КАК он работает → minor** (`0.7.0 → 0.8.0`).
  Примеры: обновлялка «обнови кит», MCP-набор из коробки, новый скилл, новый слой второго мозга.
- **Нет — только чиним и затачиваем уже поставленное → patch** (`0.7.0 → 0.7.1`).
  Сюда: багофиксы, уточнение правил/методологии, полировка хука, `.gitignore`, формулировки.
  Признак патча — **пользователю нечего осваивать**: поведение стало правильнее/чётче само собой.
- **major** (`1.0.0`) — когда владелец решит, что кит «взрослый», либо при ломающем изменении.

Спор «фича или полировка» решается **в пользу патча**, если пользователю нечего осваивать:
инфляция версий врёт о размере поставки. (Основа — SemVer: patch = обратно-совместимые фиксы;
minor = *новая* функциональность.)
