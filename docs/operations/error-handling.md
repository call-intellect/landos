## Классы ошибок

<!--
Как заполнять: раздели ошибки по классам — у каждого своё место логирования и своя реакция.
Ключевое различие: ОЖИДАЕМЫЕ (валидация ввода, 4xx — это не инцидент, метрика) vs НЕОЖИДАННЫЕ (баги, 5xx — в error-sink с алёртом).
-->

| Класс | Пример | Куда логируется | Реакция |
|---|---|---|---|
| **Ожидаемая (пользовательская)** | невалидный ввод, 4xx, отказ прав | метрика + info/warn-лог | НЕ поднимать как ошибку; смотреть на тренд метрики |
| **Транзиентная (внешняя)** | таймаут внешнего API, сетевой сбой | warn-лог + метрика ретраев | ретрай с backoff; алёрт только если превышает порог |
| **Неожиданная (баг)** | необработанное исключение, 5xx, нарушение инварианта | `<error-sink>` + error-лог + алёрт | инцидент → runbook ниже |
| **Потеря данных / деньги** | падение миграции, двойное списание, рассинхрон | `<error-sink>` PAGE + бэкап | немедленный инцидент, откат по `prod-deploy-log.md` |

## Где что логируется

- **Структурные логи** — `<log-lib>`, каждая строка с `deployment.environment`, `service.version`, `request.id` (semantic conventions — см. `analytics.md`).
- **Error-sink** — `<error-sink>`: только неожиданные (баги) и потеря данных/деньги, с привязкой к release (git SHA / тег).
- **Метрики** — счётчики ошибок по классам в `/metrics` (для трендов и алёртов).

## Runbook на инцидент

<!-- Как заполнять: пошаговый порядок действий дежурного. Ниже — скелет. -->

1. **Оценить класс и радиус.** Кого/что задело, какой tenant, с какого релиза (по `service.version` в сигнале).
2. **Стабилизировать.** Аварийный флаг (см. `feature-flags.md`, тип A) или откат релиза (`prod-deploy-log.md` → «📂 Архив применённых», найти предыдущий SHA/тег).
3. **Проверить данные.** Не пострадали ли данные; при риске — восстановление из бэкапа (Шаг 0 `prod-deploy-log.md`).
4. **Зафиксировать.** Что случилось, что сделали, что предотвратит повтор.
5. **Завести фикс.** Если корень в коде — регрессионный инвариант (см. `diagnostics-howto.template.md`, детерминированный replay), чтобы не повторилось.

## Пост-деплой ревью ошибок релиза

После **каждого** выката (см. release-теги в `prod-deploy-log.md`):

1. Отфильтровать error-sink по `service.version` = только что выкаченный SHA/тег.
2. Найти **НОВЫЕ** классы ошибок, которых не было на предыдущем релизе.
3. Каждую новую ошибку — либо в фикс, либо осознанно классифицировать (ожидаемая → понизить, транзиентная → ретрай).

```bash
# Диагностика ошибок конкретного релиза (read-only; правило №1 из prod-ssh-access.md)
{{RUNTIME_EXEC}} <error-query> --release <git-sha|deploy-tag>
```

> Связка: трассируемость «ошибка → релиз» работает только если каждый выкат получил release-тег на git SHA (`prod-deploy-log.md`, инвариант 2) и каждый сигнал несёт `service.version` (`analytics.md`).
