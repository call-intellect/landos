# plans/ — технические планы функций

> Один план = одна функция. Любая нетривиальная фича проходит воронку из четырёх стадий, прежде чем превратится в код.

## Структура

```
plans/
  analysis/      — анализ фичи: что хотим, зачем, как сейчас, аналоги, варианты (роль: feature-analyst)
  architecture/  — решение человеческим языком: что есть → что делаем → как будет выглядеть; ВЛАДЕЛЕЦ ОДОБРЯЕТ ДО ТЗ (роль: solution-blueprint)
  tz/            — техническое задание: scope, изменения, фазы, критерии приёмки (роль: tz-author)
  handoff/       — передача контекста следующему агенту (мандат + что сделано + что осталось)
  qa/            — единый реестр багов + сессии тестирования
  archive/       — завершённые или отменённые планы
  decisions-log.md — журнал спорных решений, принятых по ходу (living)
  README.md      — этот файл
```

## Воронка (4 стадии)

```
  analysis  ──►  architecture  ──►  tz  ──►  archive
  (что/зачем)    (GATE: approved)   (контракт)  (сделано)
```

1. **analysis** → `analysis/YYYY-MM-DD-<slug>.md`
   Доказательная база: что хотим, зачем, как сейчас, аналоги/лучшие практики, матрица вариантов, открытые вопросы. Ещё не решение — материал для решения.

2. **architecture** → `architecture/YYYY-MM-DD-<slug>.md`  ⟵ **ЖЁСТКИЙ GATE**
   Замысел простым языком для человека-владельца: что есть → что делаем → **как будет выглядеть** («было→стало», ASCII-макеты, живой образец). `status: draft → approved`. Владелец читает и говорит «да, именно это». **Пока не `approved` — дальше по воронке не идём.**

3. **tz** → `tz/YYYY-MM-DD-<slug>.md`
   Машинный контракт на реализацию: scope, технические изменения по слоям, фазы `[ ]`/`[x]`, критерии приёмки (EARS + Given/When/Then), риски, DoD. Пишется **только при одобренной архитектуре**.

4. **archive** → по завершении файлы всех трёх стадий переносятся в `archive/`.

## Цепочка ролей (скиллов)

```
feature-analyst  →  solution-blueprint  →  tz-author  →  tz-orchestrator
   analysis           architecture          tz            реализация
```

- **feature-analyst** — исследует рынок и код, собирает `analysis/`.
- **solution-blueprint** — переводит анализ в архитектуру человеческим языком, ведёт владельца к `approved`.
- **tz-author** — пишет ТЗ-контракт.
- **tz-orchestrator** — реализует ТЗ фаза за фазой с независимой приёмкой.

## GATE (жёсткое правило)

> **ТЗ пишется только когда существует `architecture/<slug>.md` со `status: approved`.**

Роль `tz-author` **отказывается** писать ТЗ без одобренной архитектуры. Это ловит «сделали не то, что я имел в виду» на дешёвом этапе (текст), а не на дорогом (код). Обходов нет.

## Правила

- **Имя файла:** `YYYY-MM-DD-<slug>.md`, `<slug>` в kebab-case.
- **Единый feature-slug** проходит сквозь все стадии: `analysis` → `architecture` → `tz` используют один и тот же `<slug>` в имени и во frontmatter-поле `feature`. Так связь между стадиями видна без чтения.
- **Один план = одна функция.** Если план на эту функцию уже есть — работаем с ним, новый не заводим.
- План делится на фазы, у каждой статус `[ ]` или `[x]`.
- Архитектура — для человека (простой язык, «было→стало», макеты), не машинный контракт. ТЗ — наоборот, машинный контракт.
- В конце ТЗ — итоговый блок: реализовано целиком или нет, что осталось.
- **Любой агент обязан актуализировать план** после каждой сессии (статусы фаз, итог).
- Шаблоны: `analysis/_template.md`, `architecture/_template.md`, `tz/_template.md`, `handoff/_template.md`.
