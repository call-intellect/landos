# TASK WORKFLOW — Процесс работы над задачей

## Два контура: скелет и конвейер

**Контур A — «Первый скелет»** (новый проект, день 1): `idea-interviewer` (распаковка идеи и обрезка
до ходячего скелета, ноль техвопросов) → `project-bootstrap` (стек, структура, БД по
`decision-defaults` — сам, с доказательством) → скелет задеплоен и кликабелен в первый же день.
Полной цепочки документов здесь нет: momentum важнее бюрократии.

**Контур B — «Каждая следующая фича»** (конвейер качества) — четыре фазы ниже. Роли-скиллы:
`feature-analyst` → `solution-blueprint` → `tz-author` → `tz-orchestrator` → `qa-user-tester` →
`strict-production-review-gate`.

**Лёгкая тропа.** Правка на 1–2 файла без развилок идёт прямым маршрутом (execution plan → код), без
полной цепочки. Критерий выбора маршрута — в скилле `core-engineering-standards`; сложность оценивай
до начала, а не после третьего файла.

**Проверка глазами пользователя обязательна.** Вердикт «готово» по фиче с UI даётся только после
реального прохода `qa-user-tester` через браузер — не по коду и не по зелёным тестам.

## Четыре фазы (цепочка планирования)

```
Анализ (analysis) → Архитектура (architecture, GATE: approved) → ТЗ (tz) → Реализация
```

Нельзя перейти к следующей фазе без завершения предыдущей.
**Жёсткий gate:** ТЗ не пишется, пока нет `plans/architecture/<feature>.md` со `status: approved` —
это ловит «сделали не то, что имелось в виду» на дешёвом этапе (текст), а не на дорогом (код).

---

## Фаза 1 — Анализ (`plans/analysis/`)

**Когда:** при появлении любой нетривиальной задачи.

**Что делаем:**
1. Создать `plans/analysis/YYYY-MM-DD-имя-задачи.md` по шаблону `_template.md`.
2. Исследовать: зачем, как работает сейчас, аналоги/лучшие практики, открытые вопросы.
3. Зафиксировать решения в разделе «Решения принятые в ходе анализа».

**Критерий перехода:** доказательная база собрана, открытые вопросы сведены к развилкам.

---

## Фаза 2 — Архитектура человеческим языком (`plans/architecture/`)

**Когда:** анализ завершён.

**Что делаем:**
1. Создать `plans/architecture/YYYY-MM-DD-имя-задачи.md` по шаблону `_template.md`.
2. Описать простым языком: что есть сейчас → что делаем → **как это будет выглядеть**
   (сценарии «было→стало» + макеты экранов + живой образец).
3. Развести «решения, что принял за тебя» и «что реши ты (развилки)».

**Критерий перехода (GATE):** владелец прочитал и сказал «да» → `status: approved` + `owner` + `approved_at`.
Агент **никогда** не ставит `approved` сам.

---

## Фаза 3 — ТЗ-контракт (`plans/tz/`)

**Когда:** архитектура одобрена (`status: approved`).

**Что делаем:**
1. Создать `plans/tz/YYYY-MM-DD-имя-задачи.md` по шаблону `_template.md`.
2. Заполнить scope, технические изменения, фазы, машинно-проверяемые acceptance-критерии, DoD.
3. Сослаться на architecture- и analysis-файлы (`relates_to`).

**Критерий перехода:** ТЗ самодостаточно для исполнителя (не нужно переспрашивать/угадывать).

---

## Фаза 4 — Реализация

После реализации:
1. Обновить Second Brain (заметки в `01_projects/`, `02_architecture/` при необходимости).
2. Отметить фазы ТЗ `[ ]` → `[x]`.
3. Перенести analysis + architecture + tz файлы в `plans/archive/`.

---

## Именование файлов

```
plans/analysis/YYYY-MM-DD-имя-задачи.md
plans/architecture/YYYY-MM-DD-имя-задачи.md
plans/tz/YYYY-MM-DD-имя-задачи.md
```

Имя — kebab-case, единый feature-slug сквозь все фазы. Одна задача = одна цепочка файлов.

## Статусы (frontmatter `status:`)

| Статус | Значение |
|---|---|
| `draft` | В работе |
| `approved` | Архитектура одобрена владельцем — можно писать ТЗ |
| `ready` | Фаза завершена, готово к следующей |
| `done` | Реализовано, перенесено в archive |
